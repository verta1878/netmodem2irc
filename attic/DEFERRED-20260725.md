## DEFERRED 1 — ISCmplr.dll access violation (highest value)

`wine ISCC.exe netmodem2irc.iss` -> rc=5, no output:
```
err:module:loader_init "ISCmplr.dll" failed to initialize, aborting
err:module:loader_init Initializing dlls for ISCC.exe failed, status c0000005
```
AV is in **DLL initialization**, before any .iss parsing. Display ruled out:
identical failure with Xvfb :1 confirmed reachable via xdpyinfo; the AV is in the
ISCC process while nodrv_CreateWindow errors come from a separate wineboot process.
DLL itself is well-formed: PE32 i386, ImageBase 0x800000, relocs intact, DllChar 0x0000.

Significance: this is the **second** binary in the port to AV at init (Setup.exe
being the first, per SESSION-20260725-SUMMARY). Argues against the "Wine codepage
limitation" verdict and toward a real defect in the port's init path. Likely shares
a root cause with the Setup.exe form-initialization AV.

## NOT A TASK — go32v2 removal

No go32v2 in the codebase; it appears only in the FOSSIL scoping doc as the
*rejected* option. `go32` is a Pascal unit *inside* the go32v2 RTL (DPMI wrapper),
not an alternative extender — the runtime extender for go32v2 is CWSDPMI (C).
Adopting `go32` means adopting go32v2 and moving the driver out of 16-bit real
mode, contrary to the scoping decision. Real C dependency in the DOS build is
Watt-32 + Watcom clibl.lib (`__exit_`, `__GETDS`, `__do_exit_with_msg_`).

## Open architecture question (from this session, unresolved)

netfossl as a FOSSIL **provider** (NetFoss-style: BBS -> INT 14h -> netfossl -> TCP)
is confirmed as the intent. Provider units already exist and are NOT wired to netfossl:
  engine/NM_Int14ISR.pas (181)  InstallInt14 / RemoveInt14 / Int14Handler / SetResidentUart
  engine/NM_TSRResident.pas (149)  Install / Pump / Unload
  engine/NM_FossilDriver.pas (110)  DispatchFrame / InstallFossil / RemoveFossil
  engine/NM_Fossil.pas  FossilDispatch(var U: TUart16550; ...) + FossilGetInfo (Fn 1Bh)
  + 7 test units, docs/netmodem2irc_TSR_skeleton.md, netmodem2irc_i8086_TSR_finish_guide.md
FossilDispatch already runs against an EMULATED TUart16550 with TX/RX rings -- that
ring is the substitution seam where a socket replaces hardware.

BLOCKER for a go32v2 provider: residency. 16-bit msdos RTL has {$DEFINE HAS_KEEP}
and Procedure Keep(exitcode: word); the go32v2 RTL has no equivalent. FPC's go32
docs mention TSRs only as the *other* party a protected-mode program hands a
get_rm_callback to. A DPMI host owns client lifetime, so descriptors/locked
regions/callbacks are torn down at exit. NOT proven impossible -- just undocumented
in FPC. Resolve before committing the rewrite to go32v2.

Corrected in session: conventional-memory cost is NOT an argument against go32v2 --
under DPMI code/data live in extended memory, only global_dos_alloc buffers and
rm-callback thunks sit below 1 MB. Also corrected: netfossl's current
dos/fossil_dos.pas is a FOSSIL *client* (Intr($14,R), expects X00/BNU/NetFoss
resident), which is the opposite shape from the provider intent.
